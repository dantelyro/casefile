# 0.14.0 — `fix-bug`, issues and the implementer — implementation plan

**Spec:** `docs/specs/2026-10-14-fix-bug-design.md` (approved 2026-10-14).
**Starts from:** `0a8e8f8` on `main`, version `0.13.1`.
**Ships as:** `0.14.0`.

**Goal:** a bug goes from a file in `docs/issues/` to a reviewed, merged fix on its own branch: the
`devflow:implementer` agent reproduces it with a failing test and fixes it, `devflow:reviewer` checks
it, and the main session merges after the developer's yes, following one shared merge procedure.

**How this plan is run:** in a devflow session, by the main session, one task at a time, test first;
each task committed when its tests pass (the developer's standing instruction, 2026-10-15). Never
push. Task 7 (the live test) runs on a throwaway clone of Inverso.

## Global constraints

The 0.13.0 plan's constraints hold: standard library only, Python ≥ 3.10, `unittest`, every rule
tested both ways, mutation-checked, conventional commits, each rule stated once, nothing written
into a project that has not agreed to it.

## Task 1 — `issues_status.py`

The mechanical half of issues, so it is never left to judgement (0.13.0 principle).

- [x] Tests first, on a temporary git repository with issue files:
  - **parse**: `# I-0007 — Title`, then `- Status:`, `- Found:`, `- Blocks:`, `- Related to:`, `- Rules:` lines
    and the four sections; a file that does not parse is an error naming it.
  - **list**: `open` and `in-progress` issues with the task each blocks (`none` → no block).
  - **check**: every `fixed (<commit>)` issue — the commit exists and is on the default branch
    (`git merge-base --is-ancestor`), and the test named under "Test that must fail first" exists in
    the repository (its name found in a test file). Either check failing → error, exit 1.
  - **blocks**: `--blocks <plan> <task>` → the open issues blocking that task (for `implement`).
  - **next id**: `--next-id` → the next free number, from the highest file (letter suffixes allowed).
  - `wontfix: <reason>` needs a reason; any other status is an error.
- [x] The script: standard library, JSON output with `--json`, plain text otherwise.
- **Deviation from the spec, recorded in it:** "the test passed in the last run" cannot be checked
  without a results store devflow does not have; the script checks the test **exists**, and the
  merge procedure is where it is shown passing (the suite runs before every merge commit).

## Task 3 — The implementer agent

- [x] `agents/implementer.md` from Inverso's, generalised, with the M1 lessons: inputs are a plan task
      or an issue; red → green → refactor, the test failing for the right reason first; every planned
      item and note done or listed under `NOT DONE`; bugs elsewhere reported in `NOTES`, never fixed;
      dependencies added with the package manager's command, never a hand-typed version; a throwaway
      database or service for a fresh check; installs from the lock file with the app's `install`
      command; the report block of the spec.
- [x] `model: sonnet`, `isolation: worktree`, `tools: Read, Grep, Glob, Edit, Write, Bash`.
- [x] Live check: `devflow:implementer` loads; its `git merge` and `git push` are refused; a write to
      `docs/specs/` (protected) and to `docs/issues/` is refused.

## Task 4 — `shared/merge.md`

- [x] The five steps of the spec: clean tree on the default branch; `git merge --no-ff --no-commit`;
      every touched app's `test` command, and its `image` build when the change touched the app;
      on failure `git merge --abort`; commit `merge(<scope>): <title> [<rule IDs>]` with the task's or
      issue's status updated in the same commit and minor findings written down as "accepted at
      merge"; then each app's `cleanup` command in every worktree before removing it, and the
      branches. Never `--force` without the developer's yes.
- [x] `apps.<name>.cleanup` and `apps.<name>.image` documented in the README's config section.

## Task 5 — The `fix-bug` skill

- [x] `skills/fix-bug/SKILL.md`: the issue format; the flow of the spec (issue → implementer →
      reviewer → fix loop of at most 2 rounds → merge after the developer's yes → status

- [x] Trigger evals: must fire for an issue file, for "there's a bug: …, fix it", for a bug found

## Task 7 — Live test on Inverso (throwaway clone)

0.14.0 is accepted when a real Inverso bug goes from `docs/issues/` to merged through `fix-bug`.

- [x] The bug: M1's "accepted at merge" finding — `web/tests/setup/migrate.ts` opens its admin
      connection on the base URL's database, so a `DATABASE_URL` naming a not-yet-created database
      fails before `CREATE DATABASE`.
- [x] In a clone with no remote, devflow loaded from the working copy: file the issue, run `fix-bug`
      headless with the developer's yes given in advance for this test, and check: the failing test
      came first, the reviewer ran the suite, the merge commit carries `fixed (<commit>)`,
      `issues_status.py` reports it fixed, worktrees and branches are cleaned up.
- [x] Whatever goes wrong becomes a follow-up before 0.15.0.

**Result (2026-10-16).** In a clone of Inverso with a throwaway Postgres on port 55432, `fix-bug`
filed `I-0001` (after the developer's pre-given yes), the implementer fixed both admin connections
(`migrate.ts` and the drop script, which had the same flaw) in `5959395`, the reviewer re-ran the
suite and the reproduction and approved, the merge `e92b647` recorded `fixed (5959395)` and the minor
finding under "Accepted at merge", worktrees, branches and their test databases were cleaned up, and
`issues_status.py` reported no open issues.

What went wrong, fixed in 0.14.1: the "test that must fail first" tested a new helper — red only
because the helper did not exist — so undoing the fix left the suite green; the reviewer noticed and
rated it minor. The implementer now reproduces the reported behaviour through the code the bug is in,
and the reviewer rates a bug-fix test that survives undoing the fix as major. Re-running only the
reviewer on `5959395` then gave changes-requested with both call sites as major findings.
