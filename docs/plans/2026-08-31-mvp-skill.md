# `mvp` Skill Implementation Plan — Stage 1

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the `mvp` skill — a cast of client, domain and dev-team actors dispatched at an idea
to produce `docs/purpose.md`, `docs/requirements.md` and a session record — together with the
`evidence-based-decisions` seeding split that keeps the two skills from claiming the same directory.

**Architecture:** Markdown only. `SKILL.md` states principles and phases and stays small, because it
is loaded in full whenever the skill triggers (D-001); everything long lives in `references/` and is
read only when a run needs it. Actors are system prompts assembled at runtime and passed as the
`prompt` of an `Agent` dispatch — no agent definition files, nothing registered, no restart.

**Tech Stack:** Markdown with YAML frontmatter. No build, no test suite, no dependencies — that is a
stated property of this repo in `CLAUDE.md` and this plan does not change it. Verification is
inline shell and `python` one-liners, never a new checker file.

**Spec:** `docs/specs/2026-08-31-mvp-and-project-specs-design.md`

## Global Constraints

Every task's requirements implicitly include this section.

- **Conventional commits, always** — `feat:`, `fix:`, `docs:`. `Decided by` attribution is resolved
  by filtering `git log -L` down to `feat`/`fix`; dropping prefixes breaks it permanently (D-007).
- **`name` in frontmatter must equal the directory name** — `name: mvp` in `skills/mvp/SKILL.md`.
- **No `model:` key in any `SKILL.md` frontmatter.** A skill's `model` override applies for the rest
  of the turn, not only while the skill runs (D-012). Actor model choice is per `Agent` dispatch.
- **`SKILL.md` stays at or under 120 lines.** `scaffolding/SKILL.md` is 106; that is the working
  ceiling for the tier (D-001).
- **State each rule once, in the place it applies** (D-008). A rule in a `references/` file is not
  also summarised in `SKILL.md` or the README.
- **No dependency on another plugin.** `mvp` may reference its own plugin's files by path; it may
  not reference the superpowers cache directory or any other plugin's paths (D-016).
- **`mvp` must NOT claim `/init` in this stage.** `scaffolding` still owns that trigger until it is
  deleted in Stage 3. Two skills claiming one trigger is the ambiguity the staging exists to avoid.
- **Claim tags are exactly `[reasoned]` and `[claimed — UNVERIFIED]`** — em dash, uppercase
  UNVERIFIED. Used identically across `synthesis.md`, `documents.md` and `SKILL.md`.
- **Version bump in `.claude-plugin/plugin.json` on the shipped change**, minor for a new skill.
  Claude Code refreshes marketplaces on startup; without a bump nothing updates.
- **Skill prose carries its reasons, not just its rules.** Match the register of the existing
  skills — the "Rationalizations" and "Red flags" tables exist because a rule without its reason
  gets optimised away.

- [ ] **Step 3: Write `skills/mvp/SKILL.md`**

Frontmatter — the `description` is the entire trigger surface, so it is written to match the
moment, not to summarise the skill:

```yaml
---
name: mvp
description: >
  Use when an idea for a new project needs to become something buildable — deciding what is worth
  building first, what the project is for, and what it must do. Triggers on: "what should I build
  first", "what am I missing", a feature list nobody has challenged, an idea about to be scoped, a
  project with no `docs/requirements.md`, or a brief that needs cutting to a defensible MVP. Not
  for adding a feature to a project whose requirements already exist.
---
```

Body sections, in this order, each stating its rule once and carrying its reason:

1. **`# MVP`** and a two-paragraph overview — a cast of actors is dispatched at an idea; the output
   is the smallest thing that serves the purpose, plus the record of what was cut and who wanted it.
2. **`## The three actor classes`** — a three-row table: client (from `purpose.md`, count derived),
   dev team (fixed five), domain (from the brief). One line each on what they answer. Point at
   `references/clients.md`, `dev-team.md`, `domain-actors.md` for the prompts. Do **not** restate
   the prompts here.
3. **`## Two claim types`** — the load-bearing section, stated in full because it governs everything
   the skill emits:
   - `[reasoned]` — an inference from the brief, `purpose.md`, or another actor's stated position.
     The reasoning is in the output; verify it by reading it.
   - `[claimed — UNVERIFIED]` — an assertion about the world outside your documents. below the lowest rung of the ladder in
     `evidence-based-decisions` — that ladder grades what came back from a real system, and this
     came back from nobody. Quarantined, never merged into the requirement list,
     confirmed with a real person before anything is designed around it.
   - The tag goes on the **claim, not the actor** — a client actor emits both kinds.
4. **`## Seven phases`** — a numbered list, one line each: write the brief · draft `purpose.md` ·
   propose the roster and wait · round 1 parallel and blind · synthesize · round 2 targeted ·
   cut to an MVP, refine `purpose.md`, write the documents. Name the reference each phase reads.
5. **`## Nothing is written unasked`** — the skill offers and waits. No devflow skill creates a
   document in a project that has not agreed to it.
6. **`## Red flags — stop`** — at minimum: a domain claim promoted into the requirement list without
   a human confirming it; a roster dispatched before approval; an MVP with nothing cut from it; a
   requirement with no actor attributed; `purpose.md` written after the roster instead of before.
7. **`## Rationalizations`** — a two-column table. At minimum: *"the actors agreed, so it's true"* →
   agreement among fabrications is not evidence of anything; *"I'll attribute the requirements
   later"* → by then the advocate is gone and the line reads as fact; *"the client actor is basically
   the user"* → the client owns the product, the domain actor lives in the world it is for, and their
   conflict is the most useful thing the skill produces.
8. **`## References`** — a table of the six files and when each is read.

Open with the rule that gives the file its purpose: **the brief is the ceiling on output quality.**
Every actor receives exactly this text and nothing else, so a vague brief produces a vague cast and
no amount of dispatching recovers it.

Five questions, closed and ordered, each with what its answer changes downstream:

| # | Question | What it changes |
|---|---|---|
| 1 | What is it, in one sentence a stranger would understand? | The brief's first line |
| 2 | Who is it for? Name the people, not a market segment. | The domain cast (`domain-actors.md`) |

| 5 | What is it deliberately not? | `purpose.md`'s non-goals, and the first thing cut |

before anything dispatches. State that it is shown, not just written: an unreviewed brief is a
guess that eight actors then elaborate on.

Then **`## Not asked`** — stack, framework, database, hosting, repo shape, component library. All of
it belongs to `project-specs`, and asking here invites the user to decide the build before deciding
the product. One line naming where those questions live.

Close with the same rule `questions.md` closes with: adding a question to this file is a decision;
record it.

**`## Why the client is a separate class`** — it holds the business goal and is the only actor with
standing to say *"that is phase two."* The dev team will specify everything and the domain actors
will want everything; without a client nothing gets cut, and a skill named `mvp` that cuts nothing
has failed.

**`## The count is a property of the purpose`** — not a fixed number.

| Purpose shape | Clients | Why |
|---|---|---|
| Single audience, one buyer | 1 | No internal conflict to surface |
| Two-sided (marketplace, platform) | 2 | The side wanting listings free and the side wanting them curated are not one person. An MVP serving only one is a finding, not a detail |
| Internal tool with a sponsor and users who did not ask for it | 2 | The sponsor's success criteria and the users' are routinely opposed |

State the derivation as a rule: read `purpose.md` for distinct parties whose success criteria could
conflict; one client per party; propose the count with the roster and say why that many.

**`## Why `purpose.md` is drafted first`** — the client cast cannot be derived until there is a
stated purpose to derive it from. This is the reason phase 2 precedes phase 3, and it is stated here
rather than in `SKILL.md` because this is the file that depends on it.

**`## The prompt template`** — the assembled system prompt, with the substitution points marked:

```
You are {role} — {one-line identity, including what you are accountable for}.
This is your product. You are paying for it.

Your success criteria: {from purpose.md}
Your constraint: {budget, deadline, or the political reality — from purpose.md}

You have never written software and do not know what a framework is. Do not
suggest features by name; describe outcomes you need and let others name them.

You will be shown a brief. For each thing in it, say whether it is needed for
the first usable release or whether it is phase two, and why. Say what is
missing that would stop you selling, launching or defending this.

Distinguish what you are inferring from the brief from what you are asserting
about the world. Mark the second kind explicitly — it will be checked with a
real person before anyone builds on it.
```

is for. Their conflict is the most useful thing the skill produces: the client wants the feature

here, not in `clients.md` — one rule, one place (D-008).

thing it describes. Its output is unsourced and routes to `[claimed — UNVERIFIED]` unless it is
reasoning about the brief rather than asserting about the world.

**`## What synthesis is looking for`** — three things, in this order:

1. **Contradictions** — two actors whose positions cannot both be built. The offline-write versus
   server-authoritative clash is the worked example: neither actor was wrong, they were never asked
   the same question.
2. **Undecided questions** — something no actor could answer from the brief. These become
   `purpose.md` gaps, not requirements.
3. **Single-source claims** — asserted by exactly one actor. Weak by construction; note the source
   and treat accordingly. A commercial operator's business model leaking in as a user need is the
   standing example.

**`## Tagging goes on the claim, not the actor`** — one actor emits both kinds. A client saying
*"your purpose says weekend hunters, this feature only serves guides"* is `[reasoned]`; the same
client saying *"nobody pays more than ten a month for this"* is `[claimed — UNVERIFIED]`. State the
test: does it follow from a document we have, or assert something about the world we do not?

**`## When round 2 is worth dispatching`** — only for a contradiction, only the actors in it, each
shown the other's position. Not for undecided questions (nobody has the answer) and not for
single-source claims (a second pass makes an invention more fluent, not more true). A coherent brief
costs nothing here, and that is the design working rather than failing.

**`## Resolve or hold`** — the re-dispatched actor must return one of two shapes: *"I concede X
because Y"* or *"I still hold X because Y."* A concession with no reason is noise and is recorded as
unresolved. An unresolved contradiction is a finding, not a failure — it goes in the session record
as an open decision with both positions intact.

**`## The limitation, stated so it is not rediscovered as a bug`** — blind actors find gaps in the
brief only. A gap that exists only once `backend` has proposed permission inheritance, which
`security` would catch on seeing it, is missed. Round 2 recovers some, but only where synthesis
already spotted a contradiction to chase. This is the accepted cost of not running a round table;
the reasoning is in decision D-019.
