# D-080 — A brief follows what decisions and specs settle, and never cites an ID bare

**Status:** Accepted (2026-11-19).
**Decided by:** the developer — Grade 1: asked in session on 2026-11-19, from rules they had set in their project memory

**Context:** Two rules lived only in one project's memory. Asked whether a gestor sees only assigned cemeteries, already settled by a decision, the developer answered 'why are you asking me something that was already decided?', and asked not to have it applied silently either. They also could not follow briefs citing rule and decision IDs with no text. They asked to move both into casefile: 'open casefile vscode add these'.

**Options:** (a) leave them in each project's memory; (b) shared/build-task.md, where the brief and report are written; (c) the session-start code guidelines.

**Decision:** (b). The brief states each point an accepted decision or spec rule settles, with what it says, and follows it; only what nothing settles is asked. A new Rule: an ID is never cited bare in a brief, report or question; it comes with what it says, and each option with an example. The report after building opens with the same plain-words brief: what was built, what changes for whoever uses the app, what is left; the developer: 'the brief is good before the task start, and after it finishes too'. The third memory rule, explain before doing, was already build-task's brief step (D-079).

**Trade-offs:** Briefs get longer. As with D-079, write-specs, review and evidence sessions do not get these rules unless they move to the guidelines.
