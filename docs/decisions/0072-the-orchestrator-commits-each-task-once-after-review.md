# D-072 — The orchestrator commits each task once, after review; implementers never commit and parallel mode is dropped

**Status:** Accepted (2026-11-01).
**Decided by:** dantelyro — Grade 1: decided in session on 2026-11-01, in the developer's words quoted above

**Context:** implement commits the plan only to change a task's Status (in-progress before dispatch, done after acceptance in task-by-task mode), and parallel mode lands every task with git merge --no-ff (shared/merge.md), one merge(<milestone>/<task>) commit per task. The developer called both pollution of the git history; D-069 had dropped amending the status into the task's commit as a workaround and left the design open. merge() is also outside the feat and fix prefixes D-007 attributes decisions through. The cause: the implementer commits before review, so the commit exists before the task is done, and in parallel mode the work sits on other branches that must be joined. The options were compared in session as git log graphs of one two-task milestone in each mode (task by task: 9 commits, 4 status-only; parallel: 8 commits, 2 merges, 1 status-only).

**Options:** (a) keep merges and status commits; (b) task branch + git merge --squash in every mode, one commit per task; (c) task branch + git cherry-pick -n, same history as (b) but a commit range to compute and more conflict stops in parallel; (d) git cherry-pick --ff, keeping the review fix commits, with status read from Task: trailers; (e) amend, rejected in D-069 and impossible in parallel; (f) rebase + fast-forward, which keeps the noise and rewrites the reviewed branch inside the agent's worktree; (g) no implementer worktrees and no parallel mode: the implementer leaves its work uncommitted in the developer's checkout, the orchestrator snapshots it (git add -A, write-tree, commit-tree) for the reviewer's worktree, and after approval commits that tree once.

**Decision:** (g), the developer's proposal: 'what if we drop worktrees entirelly? leave only the the reviewer on this and he never commits? he only needs to aprove and the orchestrator commits', confirmed with 'yeas that would also remove parallel mode'. Squash (b) had been chosen first in the same session and is replaced by this. Every task, in implement, fix-bug and a main-session build, becomes one commit the orchestrator writes after the reviewer approves and the developer says yes, with Status: done in the plan in that commit. In progress is the uncommitted work, kept safe under a ref outside the branches (refs/casefile/wip/<task>), never a commit on feat/. No worktrees anywhere, the reviewer's included: 'no more worktrees even on pr review'. The reviewer works in the developer's checkout, breaks code and restores it with git restore, which returns each file to the staged copy the orchestrator made; after every review the orchestrator checks that the checkout matches that copy and restores it if not. A review of a branch the developer does not have checked out switches the checkout to it first, only when it is clean. The committed tree is the tree the reviewer approved. Before settling, the developer had the two commit models simulated with real git (implementer commits: 5 commits for two tasks, a review round listed as a bug fix in semantic-release notes; orchestrator commits: 2) and chose 'the orchestrator only is best ... i decided'.

**Trade-offs:** No parallel tasks: a milestone is built one task at a time. Review fix rounds never reach history. Work is uncommitted until approval, so the wip ref is what protects it from a crash or a stray checkout. The implementer's prompt and a guard must stop it committing; the pre_commit gate moves to the orchestrator's commit. A rejected task is discarded, not reverted. A break the reviewer leaves behind now lands in the developer's checkout, not a throwaway worktree (D-045's reason for the worktree); the orchestrator's check after review is what catches it. The developer's checkout is busy for the whole task, review included. Not yet built: implement, review, fix-bug, shared/merge.md, the implementer and reviewer agents, guard_paths and guard_bash, and plan_status.py still follow the old flow until specs are written and the change is built.
