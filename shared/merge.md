# Merging a reviewed change

Used by `fix-bug` and `implement`. The main session merges; agents never do (D-031). One change at a
time, and only after the developer's explicit yes for that change — a yes for one task is not a yes
for the next.

## Before asking

Show the developer one line per change: what it is (task or issue), its rules, its files, the
reviewer's verdict and summary, and its minor findings. Wait for the yes. The developer may approve
several changes at once; merge them one by one all the same.

## Steps

1. **Clean and current.** `git status --porcelain` is empty and the current branch is the default
   branch (`.claude/devflow.json`, else `main`). Otherwise stop and say what is in the way.
2. **Merge without committing.** `git merge --no-ff --no-commit <branch>`. A conflict → `git merge
   --abort`, tell the developer which files conflict, and stop. With their yes, the change is redone
   by a new implementer starting from the current default branch, and reviewed again (`implement` says
   how). Never resolve it yourself, and never inside an agent's worktree.
3. **Prove it on the default branch.**
   - Install first: each touched app's `install` command, run on the default branch, so the tests
     run against the merged lock files.
   - Tests: every app the change touches runs its `test` command. With `apps` configured, the commit
     in step 4 runs them through the pre-commit gate; without, run them yourself now. Before running
     them, check that nothing else holds the services the tests use (`docker ps`: an agent's test
     database on the same port makes two suites fail each other).
   - Images: if the change touched an app's folder or a container definition and the app has an
     `image` command, run it. A green suite has passed with a broken image before.
   - Anything fails → `git merge --abort`, mark the task or issue blocked with the reason, tell the
     developer.
4. **Commit, with the record in the same commit.**
   - Plan task: `Status: done (<implementer commit>)` in the plan file.
   - Issue: `- Status: fixed (<implementer commit>)` in the issue file. The implementer's commit is on
     the default branch once merged, and a commit cannot carry its own id.
   - Minor findings merged unfixed are written where the task or issue lives, under "Accepted at
     merge", so the next task can pick them up.
   - `git add` those files, then `git commit -m "merge(<scope>): <title> [<rule IDs>]"`, e.g.
     `merge(M2/T3): score required skills at 70% [MATCH-010]` or `merge(I-0007): keep the uploaded
     file [CV-002]`. No co-author or "generated by" lines.
5. **Clean up every worktree the change used** — the implementer's and every reviewer's
   (`git worktree list`). For each, first run each app's `cleanup` command inside it (a per-checkout
   test database, for example), then `git worktree remove <path>` and `git branch -d <branch>`.
   Never `--force` or `-D` without the developer's yes; if removal refuses, show why.
6. **After an issue,** run `issues_status.py` (the `fix-bug` skill says where) and show its result.

Never push. Pushing is the developer's.
